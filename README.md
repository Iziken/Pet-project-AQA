# Автотесты PomidorQA

Набор автотестов на [PomidorQA](https://aiqa.su/pomidorqa) — сервис 25-минутных встреч для QA/IT-специалистов: регистрация, профиль с навыками, слоты доступности, каталог участников, бронирование и отмена встречи.

Продукт тестируется как чёрный ящик: исходного кода приложения у набора нет, доступен только живой стенд. Поэтому покрытие считается от функциональных требований, а не от строк кода.

## Что проверяет проект

Основной бизнес-риск продукта — встреча, о которой договорились два человека. Она не должна теряться, дублироваться и доставаться двоим одновременно. Вокруг этого построен набор:

- сквозной путь «зарегистрировался → заполнил профиль → открыл слот → нашёл в каталоге → забронировал → увидел встречу у обоих участников»;
- гонка за один слот: подтверждённой остаётся ровно одна бронь;
- освобождение слота после отмены и повторное бронирование другим участником;
- границы роли: гость смотрит каталог, но бронировать не может.

Дополнительно проверяются правила профиля, навыков, доступности слотов, каталога участников, бронирования, отмены и списка встреч.

## Архитектура

```text
tests/unit/      чистые функции — без сети и браузера
tests/api/       бизнес-правила и HTTP-контракт — без UI
tests/e2e/       пользовательские сценарии в браузере
tests/helpers/   тестовые данные, Arrange через API, cleanup
tests/pages/     Page Object: локаторы и действия одного экрана
docs/            матрица покрытия требований
```

Разделение жёсткое: в spec — сценарий и проверки, в helper — пользователь, в Page Object — экран. Локаторов в spec нет, `expect` в Page Object нет.

Уровень выбирается по риску, а не по привычке: правила брони дешевле проверять запросом, а не кликами, поэтому они живут на API-уровне. UI отвечает за то, что человек реально видит.

Оговорка про пирамиду: unit-уровень во внешней автоматизации проверяет собственный код набора, а не продукт. Широкое основание пирамиды здесь недостижимо, и это осознанный компромисс, а не недоработка.

## Как запустить

Команды запуска в матрице не зафиксированы, поэтому здесь не указываются непроверенные команды.

Пример структуры команд, которую нужно заменить на фактическую из репозитория:

```bash
npm ci

npx playwright install --with-deps chromium

npm run gate
npm run metrics
npm run report
```

Стенд, указанный в матрице:

```text
https://aiqa.su/pomidorqa
```

## Известные дефекты

Расхождения требований и продукта не спрятаны ради зелёного отчёта. Тесты на них написаны по требованию и помечены `test.fail()`: пока дефект жив, ожидаемый результат — падение, а когда продукт починят, Playwright сообщит `expected to fail, but passed`.

| ID   | Требование                                                 | Что происходит на самом деле                                                                                        |
| ---- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| KD-3 | R8.3 — поиск фильтрует по навыкам из раздела «могу помочь» | Фильтр ищет по навыкам обоих типов. По запросу находится также участник, который только хочет разобрать этот навык. |

KD-3 относится к требованию R8.3. Требование ограничивает поиск навыками из раздела «могу помочь», но фактический фильтр проходит по всем навыкам участника.

В матрице отдельно отмечено, что прежний зелёный тест фиксировал реализацию как правильную и тем самым скрывал расхождение. Он заменён на `test.fail()` по требованию.

## Закрытые дефекты

Два расхождения после аудита были исправлены в продукте.

### KD-1 — часовой пояс профиля не применялся к слотам → исправлено

Требование R5.5: время слотов показывается в часовом поясе владельца.

До исправления хост создавал слот на 12:00 и видел 12:00, а гость на странице хоста видел 15:00. После исправления часовой пояс владельца учитывается при создании и отображении слота — в собственных слотах, календаре на странице участника и в «Моих встречах».

Тест: `e2e/slot-timezone`.

Отдельно матрица отмечает, что unit-тест `formatSlotTime` не доказывал корректность PomidorQA, поскольку проверял учебную функцию из `src/pyramid/slots.ts`, а не код продукта.

### KD-2 — отмену можно было сделать в последний момент → исправлено

Требование R11.2: отмена запрещена позднее чем за 2 часа до начала.

До исправления функция проверяла только то, что отменяющий является участником встречи, но не проверяла время до начала. После исправления функция возвращает `cancel_window_closed`, если до начала осталось меньше двух часов, а страница «Мои встречи» показывает причину отказа.

Тест: `e2e/cancel-window`.

## Ограничения black-box покрытия

Два требования имеют статус `out of scope`.

### R7.1 — фиксированная длительность слота 25 минут

`end_time` не выводится в интерфейс. Надпись «25 минут» в интерфейсе является текстом макета, а не вычисленной длительностью.

Для проверки фактической длительности нужен доступ к БД или API, поэтому через доступный black-box интерфейс это правило доказать нельзя.

### R9.3 — прошедшие слоты не показываются

Продукт не позволяет создать слот в прошлом, а ждать естественного перехода существующего слота в прошлое для регрессионного прогона непрактично.

Для проверки такого состояния требуется подготовка данных в БД.

# Автотесты PomidorQA

[![CI](https://github.com/lebed52/pomidorqa-course-tests/actions/workflows/playwright.yml/badge.svg)](https://github.com/lebed52/pomidorqa-course-tests/actions/workflows/playwright.yml)

Набор автотестов на [PomidorQA](https://aiqa.su/pomidorqa) — сервис 25-минутных встреч для QA/IT-специалистов: регистрация, профиль с навыками, слоты доступности, каталог участников, бронирование и отмена встречи.

Продукт тестируется как чёрный ящик: исходного кода приложения у набора нет, доступен только живой стенд. Поэтому покрытие считается от функциональных требований, а не от строк кода.

## Что проверяет проект

Основной бизнес-риск продукта — встреча, о которой договорились два человека. Она не должна теряться, дублироваться и доставаться двоим одновременно. Вокруг этого построен набор:

- сквозной путь «зарегистрировался → заполнил профиль → открыл слот → нашёл в каталоге → забронировал → увидел встречу у обоих участников»;
- гонка за один слот: подтверждённой остаётся ровно одна бронь;
- освобождение слота после отмены и повторное бронирование другим участником;
- границы роли: гость смотрит каталог, но бронировать не может.

Дополнительно проверяются правила профиля, навыков, доступности слотов, каталога участников, бронирования, отмены и списка встреч.

| Область            | Проверка                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Регистрация и вход | обязательные поля, пароль не короче 8 символов, занятый email, профиль с именем из формы и поясом `Europe/Moscow`, одинаковая ошибка входа, сессия держится и закрывается |
| Профиль и навыки   | имя, Telegram, часовой пояс и «о себе» сохраняются и переживают перезагрузку; типы навыков, дубликаты, пустые значения, удаление                                          |
| Слоты              | создание, статусы `free`/`booked`, удаление свободного слота, запрет удаления забронированного                                                                            |
| Каталог            | в выдаче только участники со свободными слотами, поиск по навыку, пустая выдача, участник не видит себя                                                                   |
| Страница участника | имя, «о себе», навыки обоих типов и свободные слоты; забронированные слоты скрываются                                                                                     |
| Бронирование       | путь «нашёл → забронировал → встреча у обоих», гонка за слот (ровно одна бронь), свой слот нельзя, закрытие окна не создаёт бронь                                         |
| Отмена             | обе стороны могут отменить, запрет позднее чем за 2 часа до начала, статус «отменено» видят оба после перезагрузки                                                        |
| Мои встречи        | списки «Ближайшие» и «Прошедшие и отменённые»                                                                                                                             |
| Границы роли       | гость смотрит каталог и слоты, но не бронирует и не входит в приватные разделы                                                                                            |
| Кросс-браузерность | Chromium, Firefox, WebKit                                                                                                                                                 |

## Архитектура

```text
tests/unit/      чистые функции — без сети и браузера
tests/api/       бизнес-правила и HTTP-контракт — без UI
tests/e2e/       пользовательские сценарии в браузере
tests/helpers/   тестовые данные, Arrange через API, cleanup
tests/pages/     Page Object: локаторы и действия одного экрана
docs/            матрица покрытия требований
```

Разделение жёсткое: в spec — сценарий и проверки, в helper — пользователь, в Page Object — экран. Локаторов в spec нет, `expect` в Page Object нет.

Уровень выбирается по риску, а не по привычке: правила брони дешевле проверять запросом, а не кликами, поэтому они живут на API-уровне. UI отвечает за то, что человек реально видит.

Оговорка про пирамиду: unit-уровень во внешней автоматизации проверяет собственный код набора, а не продукт. Широкое основание пирамиды здесь недостижимо, и это осознанный компромисс, а не недоработка.

### Как выглядит тест

Скелет happy path из `tests/e2e/booking-flow.spec.ts` (полная версия — в файле):

```ts
test("гость бронирует свободный слот хоста — встреча видна у гостя и у хоста", async ({
  browser,
}) => {
  const skillTag = makeRandom("Playwright-demo"); // уникальный навык на прогон
  const host = makeUser("host", Date.now()); // уникальный пользователь на прогон
  const guest = makeUser("guest", Date.now());

  const hostSession = await openBookingSession(browser); // изолированный контекст UTC + страница + Page Object
  const guestSession = await openBookingSession(browser);

  try {
    await test.step("Хост: регистрируется, добавляет навык и слот", async () => {
      await prepareHost(hostSession.page, host, skillTag); // Arrange через служебный API + UI
    });

    await test.step("Гость: бронирует первый слот хоста" /* ... */);

    await test.step("Гость: видит встречу в «Мои встречи»", async () => {
      const meeting = await guestSession.bookingPage.openUpcomingMeetings(
        host.name,
      );
      await expect(meeting).toBeVisible();
    });
  } finally {
    await cleanupUsersViaApi([hostSession.context, guestSession.context]); // уборка даже при падении
  }
});
```

## Как запустить

Команды — из `package.json` и `playwright.config.ts` этого репозитория:

```bash
npm ci
npx playwright install --with-deps chromium firefox webkit

npm run lint        # ESLint по tests/ — правила стабильности Playwright
npm run typecheck   # TypeScript без эмита
npm test            # все проекты: unit → api → e2e × 3 браузера
npm run test:unit   # только чистые функции
npm run test:api    # только мок-сервер бронирования
npm run test:e2e    # e2e в Chromium
npm run test:e2e -- --project=e2e-firefox   # e2e в Firefox
npm run test:e2e -- --project=e2e-webkit    # e2e в WebKit
npm run gate        # typecheck + lint + все тесты
npm run metrics     # сводка по playwright-report/results.json
npm run test:traceability  # сверка матрицы покрытия с фактическими тестами
npm run report      # HTML-отчёт последнего прогона
```

Стенд по умолчанию — продакшен `https://aiqa.su/pomidorqa`. Переопределяется переменной:

```bash
POMIDORQA_BASE_URL=http://localhost:3000 npm run test:e2e
```

## Если тест упал

Сначала отличить дефект от среды — у общего живого стенда они дают разные симптомы:

- **Дефект**: тест стабильно падает в одном и том же месте, повторные прогоны не спасают. Смотреть трейс: `npx playwright show-report` или `npx playwright show-trace test-results/<папка>/trace.zip` — там DOM-снапшот каждого шага, сеть и скриншот;
- **Среда**: `connect ETIMEDOUT` к стенду, «Test ended» внутри ожидания, падение только на параллельных прогонах. Лечение — не правки теста, а перезапуск с меньшим числом воркеров (`--workers=1`).

Артефакты падения (trace, скриншот, видео) пишутся только при падении (`retain-on-failure`) и лежат в `test-results/`. Локально `retries: 0` — флак виден сразу, а не прячется за перезапуском; в CI один retry, чтобы отличить шум от воспроизводимого падения.

Повторяющиеся гонки гидратации (клик по ещё не ожившей странице проглатывается) в этом наборе лечатся в коде повтором действия через `expect(...).toPass()` — это безопасно: дубликат навыка продукт отбрасывает, а слоты перечитываются с сервера. Фиксированные паузы для этого не используются — `waitForTimeout` запрещён правилами линтера.

Дисциплина общего стенда, из-за которой набор остаётся зелёным под нагрузкой: у каждого теста свои пользователи с уникальными email (`makeUser`), в CI один worker, а cleanup удаляет аккаунты через служебный API даже при падении теста.

## CI Pipeline

GitHub Actions запускает проверки при `push` в `main`, Pull Request в `main` и вручную через `workflow_dispatch`.

### CI Flow

| Этап                       | Что запускается                                        | Условие                                      |
| -------------------------- | ------------------------------------------------------ | -------------------------------------------- |
| **1. Static Analysis**     | TypeScript + ESLint                                    | Запускается первым                           |
| **2. Tests & Performance** | Unit + API + E2E + Lighthouse + Трассировка требований | После успешного Static Analysis, параллельно |
| **3. Reporting**           | Telegram + DORA Metrics                                | После завершения всех проверок               |

### CI Jobs

| Job                          | Проверяет                              | Команда                               |
| ---------------------------- | -------------------------------------- | ------------------------------------- |
| **Lint & Type Check**        | TypeScript + ESLint                    | `npx tsc --noEmit` · `npm run lint`   |
| **Unit Tests**               | Изолированные функции                  | `npm run test:unit`                   |
| **API Tests**                | API и контракты данных                 | `npm run test:api`                    |
| **UX Performance**           | Performance + Core Web Vitals          | `lhci autorun`                        |
| **E2E Tests**                | Пользовательские сценарии (Chromium)   | `npm run test:e2e`                    |
| **Requirement Traceability** | Матрица покрытия ↔ фактические тесты   | `node scripts/check-traceability.mjs` |
| **Reports**                  | HTML / JSON / JUnit                    | Автоматически (шаг в e2e-джобе)       |
| **Notifications**            | CI status + DORA Metrics               | Telegram                              |

Перед e2e выполняется **проба стенда**: если `aiqa.su/pomidorqa` недоступен, джоба падает
сразу с понятным `::warning` вместо 20 минут полотна ETIMEDOUT. После прогона сводка
метрик (`npm run metrics`) дописывается в **Step Summary** — результат виден на странице
прогона без скачивания артефакта.

### Ночной прогон

Отдельный workflow `nightly.yml` — по расписанию (`cron: 30 3 * * *`, работает на ветке
по умолчанию) и вручную через `workflow_dispatch`:

- **Guard** — джоба-страж перед тестами: сравнивает SHA репозитория с последним ночным
  прогоном и хэш билда стенда (идентификатор Next.js в разметке — меняется только при
  деплое продукта) с закэшированным. Если ничего не изменилось и прошлый прогон был
  зелёным — тесты пропускаются, минуты не тратятся. Падение прошлого прогона даёт
  повторный: поломка не должна «пропасть» из-за отсутствия новых коммитов. Флаг `force`
  в ручном запуске включает прогон мимо стража;
- **Cross-browser** — e2e в Firefox и WebKit (matrix-стратегия, параллельные джобы). На PR гоняется только Chromium, чтобы не удлинять проверку;
- **Анти-флак** — booking-сценарии с `--repeat-each=5` и одним worker'ом; retries выключены намеренно — задача поймать флак, а не замаскировать;
- **Telegram-уведомление** — итог ночи в общий канал, включая «пропущено — изменений нет».

### Reports & Artifacts

- **HTML** — Playwright Report
- **JSON** — `playwright-report/results.json` (источник для `npm run metrics`)
- **JUnit** — `playwright-report/results.xml`
- **E2E artifacts** — screenshot, trace, video on failure
- **GitHub Artifact** — `playwright-report/` из e2e-джобы (JSON/JUnit в артефакте — только e2e-результаты), retention **14 дней**

### Оптимизации и зависимости CI

- **Concurrency**: новый push в тот же PR отменяет старый прогон — очередь не копится.
- **Guard ночного прогона**: если с прошлого прогона не изменилось ни в репо, ни на стенде — тесты пропускаются, минуты не тратятся (подробнее — «Ночной прогон»).
- **Кэш браузеров**: Chromium кэшируется по версии Playwright (`actions/cache`), промах кэша только при обновлении версии — экономия ~1.5 мин на прогон.
- **Lighthouse**: конфиг `lighthouserc.json`, аудит `https://aiqa.su/pomidorqa`, бюджеты (performance/accessibility/best-practices ≥ 80) в режиме `warn` — не блокируют деплой.
- **Secrets** (Settings → Secrets and variables → Actions): `TELEGRAM_CHAT_ID`, `TELEGRAM_BOT_TOKEN` — уведомления; `LHCI_GITHUB_APP_TOKEN` — статусы Lighthouse в GitHub. Без Telegram-секретов упадёт джоба notify; Lighthouse без токена работает — не создаёт только статусы в PR.

## Покрытие требований

[Матрица покрытия требований](docs/coverage-matrix.md)

| Статус         | Требований |
| -------------- | ---------: |
| `automated`    |         40 |
| `partial`      |          8 |
| `не покрыт`    |          0 |
| `out of scope` |          2 |
| **Всего**      |     **50** |

Непокрытых требований не осталось: каждый пункт либо закрыт автотестом, либо имеет
определённый частичный статус с планом добивки, либо честно помечен `out of scope`
(детали — в [матрице](docs/coverage-matrix.md)).

Частично покрытые (8): R5.1, R5.5, R6.4, R7.2, R8.3, R10.3, R11.3, R12.3 —
у каждого покрыта наблюдаемая часть правила, полный список «что покрыто / чего не хватает» —
в [матрице](docs/coverage-matrix.md).

Главная метрика — определённый статус у каждого требования, а не «100% покрытие» без привязки к требованиям.

В детальной матрице статус `automated` означает, что есть автотест, который падает при нарушении поведения; `partial` — что покрыта только наблюдаемая часть правила; `known defect` — что требование не выполняется продуктом и тест помечен `test.fail()`; `out of scope` — что состояние нельзя проверить через доступные интерфейсы продукта.

## Метрики набора

| Метрика                       | Значение                                                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Тестов всего                  | **50** (unit 10 / api 8 / e2e 32)                                                                                                 |
| Время полного прогона         | ~7 мин, два worker'а (e2e на трёх браузерах)                                                                                      |
| Flaky rate                    | 10×-гейты по каждому спеку зелёные; общий 10× прогон — 499/500 (единственное падение — гонка навигации — устранено после прогона) |
| E2E с Arrange через API       | 10 из 10 файлов                                                                                                                   |
| E2E с гарантированным cleanup | 10 из 10 файлов                                                                                                                   |

Замеры уровней (каждый уровень — отдельный полный прогон против живого стенда):

| Уровень        | Объём | Результат | Время   |
| -------------- | ----- | --------- | ------- |
| Unit           | 10    | 10 passed | 0.5 s   |
| API            | 8     | 8 passed  | 0.9 s   |
| E2E / Chromium | 32    | 32 passed | 2.0 min |
| E2E / Firefox  | 32    | 32 passed | 2.3 min |
| E2E / WebKit   | 32    | 32 passed | 2.3 min |

Первый прогон WebKit дал 30/32 (холодный старт движка: медленная гидратация и гонка
навигаций), повторный — 32/32. `npm test` прогоняет e2e на всех трёх браузерах, поэтому
CI стал длиннее — каждый PR проверяется в Chromium, Firefox и WebKit.

Как получены:

- количество тестов — `npx playwright test --list` по каждому проекту;
- время уровней — отдельные полные прогоны каждого проекта против живого стенда;
- flaky rate — десятикратные прогоны `--repeat-each=10` по каждому спеку на финальном коде,
  плюс общий 10× прогон всего набора;
- Arrange/cleanup — по коду: каждый e2e-файл регистрирует пользователей через служебный API
  и удаляет их в `afterEach`/`finally` даже при падении теста.

## Ограничения black-box

Два требования недостижимы через интерфейсы продукта и помечены `out of scope` (обоснование — в матрице): R7.1 — фактическая длительность слота не выводится в UI, R9.3 — прошедшие слоты нельзя создать средствами продукта, чтобы проверить их скрытие.

## Роль AI-агентов

В рабочем пространстве проекта настроен агент-писатель (`.zcode/skills/ai-avtomatizator`):

- пишет и правит тесты по правилам `CODEX.md`: spec/helper/page, `test.step`, уникальные данные, запрет `waitForTimeout` и `force`;
- локаторы для новых E2E собирает по реальному DOM живого стенда, а не по исходникам;
- обязан прогнать ESLint и десятикратный `--repeat-each` нового теста на флапы перед отчётом;
- уборка данных — служебным API стенда, аккаунты удаляются даже при падении теста.

Что агент не решает: выбор уровня проверки, приоритет по риску, статус расхождения
требований и продукта, approve и merge. Последнее слово за человеком.

Текущая ветка переработана и расширена: e2e-уровень вырос с 12 сценариев в 4 файлах до 32 в 10 — добавлены многопользовательские сценарии с изолированными контекстами, гонка за слот, границы роли гостя, жизненный цикл слотов, правила регистрации и окно отмены; общие Arrange/cleanup-хелперы (`prepareHost`, `openBookingSession`, `cleanupUsersViaApi`) и Page Object'ы для всех экранов; матрица трассировки 50 требований к фактическим тестам; e2e в трёх браузерах; CI с typecheck, lint, Lighthouse, Telegram-уведомлениями, DORA-метриками и ночным кросс-браузерным прогоном со стражем изменений; machine-readable отчётность (JSON/JUnit) со сводкой метрик.

Дополнительные тесты, архитектура, CI, метрики и документация развивались итеративно в AI-assisted workflow: локаторы собирались по реальному DOM живого стенда, каждое изменение проходило typecheck, ESLint и десятикратные прогоны на флапы. Изменения подтверждаются code review, автоматическими quality gates и трассировкой каждого требования к фактическому тесту в матрице.

# Матрица покрытия PomidorQA

Покрытие считается по функциональным требованиям MVP из [`requirements.md`](../requirements.md), а не по числу
файлов и не по строкам кода продукта. Playwright тестирует PomidorQA как чёрный ящик, поэтому
code coverage здесь измерить нечем: исходники приложения в этот репозиторий не входят.

Каждое требование получает один из пяти статусов.

| Статус         | Что означает                                                                            |
| -------------- | --------------------------------------------------------------------------------------- |
| `automated`    | есть автотест, который падает, если поведение сломается                                 |
| `partial`      | покрыта наблюдаемая часть правила, серверная или скрытая — нет                          |
| `не покрыт`    | на текущей ветке нет теста, который упадёт при поломке требования                       |
| `known defect` | требование не выполняется продуктом; тест написан по требованию и помечен `test.fail()` |
| `out of scope` | состояние недостижимо через интерфейсы продукта, black-box проверить нечем              |

## Известные дефекты

Тесты на дефекты написаны по требованию, а не по фактическому поведению, и помечены
`test.fail()`. Пока дефект жив, ожидаемый результат — падение, и прогон остаётся зелёным.
Когда продукт починят, Playwright скажет «expected to fail, but passed» — это сигнал
снять пометку. Так дыра не пропадает из отчёта и не превращается в зелёную галочку.

### KD-3 — каталог ищет по навыкам обоих типов

Требование R8.3 ограничивает поиск разделом «могу помочь», фильтр каталога проходит по всем
навыкам участника. По запросу «Playwright» находится и тот, кто Playwright только хочет
разобрать. Требует решения продукта: сузить фильтр или переписать требование.

Важно: до аудита в наборе жил зелёный тест «поиск находит специалиста по обоим типам
навыков». Он фиксировал реализацию как правильную и прятал расхождение — такой тест
опаснее отсутствующего. Он заменён на `test.fail()` по требованию.

## Закрытые дефекты

Два расхождения после аудита исправлены в продукте — это и есть смысл такой матрицы:
она не отчёт для галочки, а список задач, по которому видно, что именно менять.

### KD-1 — часовой пояс профиля не применялся к слотам → исправлено

Требование R5.5. Хост создавал слот на 12:00 и видел у себя 12:00, а гость на странице
хоста — 15:00. Время слота хранится как абсолютный момент, но владельцу форматировалось
на сервере (UTC), а гостю — в браузере, в его собственном поясе. Поле `timezone` в профиле
сохранялось и не использовалось при отображении нигде.

Что изменилось в продукте: пояс владельца участвует и при создании слота (введённые дата
и время читаются как локальные для его пояса), и при отображении — в своих слотах, в
календаре на странице участника и в «Моих встречах». Рядом с календарём появилась подпись,
в чьём поясе показано время. Тест: `e2e/slot-timezone`.

Отдельно стоит отметить ловушку, которую этот дефект вскрыл: unit-тест `formatSlotTime`
всё это время был зелёный, потому что проверяет учебную чистую функцию из
`src/pyramid/slots.ts`, а не код продукта. Зелёный unit-уровень здесь ничего не доказывал
про PomidorQA.

### KD-2 — отмену можно было сделать в последний момент → исправлено

Требование R11.2 и негативный критерий приёмки «нельзя отменить бронирование за час до
звонка». Функция `pomidorqa_cancel_booking` проверяла только, что отменяющий — участник
встречи, времени до начала не смотрела.

Что изменилось в продукте: функция отказывает с `cancel_window_closed`, если до начала
меньше двух часов, а страница «Мои встречи» показывает человеку причину отказа.
Тест: `e2e/cancel-window`.

## Уровни проверок

| Уровень | Тестов | Что проверяет                                                                 |
| ------- | ------ | ----------------------------------------------------------------------------- |
| unit    | 10     | чистые функции набора: пересечение слотов, валидация пароля, формат времени   |
| api     | 11     | бизнес-правила брони на мок-сервере + служебный API регистрации живого стенда |
| e2e     | 34     | пользовательские сценарии в браузере на `aiqa.su/pomidorqa`                   |

Честная оговорка про пирамиду: unit-уровень здесь проверяет **наш собственный** код, а не
продукт — исходников PomidorQA у набора нет. Поэтому широкое основание пирамиды в этом
проекте недостижимо в принципе, и это нормально для внешней автоматизации чёрного ящика.
Правила брони, которые дешевле всего проверять ниже UI, вынесены на API-уровень.
